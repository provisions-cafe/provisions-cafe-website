## 2. ⚠️ Next.js 16 divergences from `CMS-GUIDE.md` (which is Next 15)

The guide is written for Next 15. These differences are **confirmed** and MUST
be honored — porting the guide verbatim will break:

1. **`middleware.ts` → `proxy.ts`.** ✅ DONE. The auth gate lives in **`proxy.ts`**
   at repo root. Uses a named `export function proxy(req)` + `export const config`.
   Docs confirmed: `16-proxy.md` + `02-guides/authentication.md`. **Decision:** the
   `matcher` is scoped to `["/admin", "/admin/:path*"]` only (a *divergence* from the
   guide, which runs on all routes). Rationale: public pages must never touch
   Supabase, so they stay resilient/fast; and Next 16 proxy runs on the Node runtime,
   so the service-role profile lookup works there. Supabase calls in `proxy.ts` are
   wrapped in try/catch and fail closed (→ login / permission-less employee).
2. **`cookies()` is async** — ✅ awaited in `server.ts`; proxy uses request-cookie
   wiring (`getAll`/`setAll` rebuild the response so refreshed cookies persist).
3. **Caching / revalidation.** ✅ RESOLVED. `next.config` has **no
   `cacheComponents`**, so `use cache`/`cacheTag`/`revalidateTag` do NOT apply —
   use the guide's **`revalidatePath(...)`** in server actions (confirmed still
   valid in Next 16's `07-mutating-data.md` / `09-revalidating.md`). For settings
   (header/footer/JSON-LD on every page) use `revalidatePath("/", "layout")`.
4. **Server Actions** — ✅ confirmed. `"use server"` file/function directive;
   verify auth INSIDE every action (they're reachable via direct POST); return
   `{error}` never throw; then `logActivity` + `revalidatePath`.

## 4. Current content model → target DB model (the migration map)

This is the concrete mapping a new session needs to build the schema + seed.

### 4.1 Menu — currently hardcoded JSX, becomes 2 collections
- **Where it lives now:** `app/menu/page.tsx` — a wall of `<MenuItem .../>`
  components (from `components/menu.tsx`) grouped by `<MenuHeading>` into
  categories, laid out in **3 columns**.
- **Categories present (in order):** Breakfast · Wraps & Focaccia · Small Plates
  · Sandwiches & Burgers · Mains · Salads · Sides · Dessert · Kids Meal.
- **`MenuItem` prop shape** (→ becomes item columns):
  `name` (text), `price` (text like `"$27.50"` — keep as text, prices carry `$`),
  `desc` (text, optional), `tags` (`text[]`, e.g. `["V","GFA","GF"]`), `sub`
  (text, optional, renders as `(…)`).
- **Dietary tag legend** (on menu page): V = Vegetarian, GF = Gluten free,
  GFA = Gluten free available.
- **✅ BUILT** in `supabase/menu.sql` (RLS per CMS-GUIDE §4.2; seeded by `seed.sql`):
  - `menu_categories`: `id`, `name`, `slug` (unique), `column_group` (int 1–3),
    `display_order`, `is_published`, timestamps.
  - `menu_items`: `id`, `category_id` (fk, `on delete cascade`), `name`,
    `price` (text), **`description`** (⚠️ renamed from `desc` — `desc` is a SQL
    reserved word; map DB `description` → `MenuItem`'s `desc` prop in `lib/menu.ts`),
    `sub`, `tags` (`text[]`), `is_highlight` (bool), `highlight_group` (text),
    `highlight_order` (int), `display_order`, `is_published`, timestamps.
  - Public read = `is_published = true`; any authed user full CRUD; `touch` trigger.

### 4.2 Home menu highlights — subset shown on the homepage

### 4.3 Business info + hours → `site_settings` singleton override

- **Build:** `lib/settings.ts` (client-safe types + `SETTINGS_DEFAULTS` mirroring

- **⚠️ `site_settings.data` JSON shape is already seeded** (`supabase/seed.sql`) —

  `{ urls:{book,order,directions,reviews,mapEmbed}, contact:{phoneDisplay,phoneHref,
  addressLine1,addressLine2}, business:{name,streetAddress,locality,region,postalCode,
  country,latitude,longitude,priceRange,ratingValue,reviewCount,telephoneE164},
  hours:[{day,label,time,closed}] (Mon-first, 7 entries),
  whatsOn:{intro, cards:[{title,text}]} }`. `NAV_ITEMS` stays in code (not in v1).
  Settings actions revalidate via `revalidatePath("/", "layout")`.
- **Consumers to rewire** (grep `site-data` importers): `SiteHeader.tsx`,

### 4.5 Photos → `image_overrides` slot table + `media` bucket
- **Where they live now:** `public/uploads/*.webp` (18 files: bar, barista,

  `app/functions/page.tsx`, `app/our-story/page.tsx`,
  `components/gallery/GalleryGrid.tsx`, `components/home/Hero.tsx`.
- **Component already supports swapping:** `components/ImageSlot.tsx` renders
  `src` when supplied, else a placeholder — good hook for override-by-slot.
- **Approach (override-over-default):** an `image_overrides` table keyed by a
  stable **slot id** (e.g. `home.hero`, `home.dining-room`, `gallery.mural`),
  storing an optional `url`. A helper merges DB overrides over the hardcoded
  `/uploads/*.webp` defaults; if no row, the code default renders. Uploads go to
  a public `media` bucket via `ImageUploader.tsx` (client, WebP-convert first),
  storing `getPublicUrl()` into the slot row. See CMS-GUIDE §4.4 & §12.
- **Task:** enumerate & name every swappable slot across those 5 files (stable
